# Vue 3 前端编码规范（工作区试点）

在 Vue 3 的代码生成或修改任务中使用本 Skill。开发者可显式调用
`$frontend-coding-standards`；符合描述的 Vue 3 前端任务也应自动匹配。每次实际
启用后，在交付反馈中说明触发方式是“显式”还是“自动”。

## 适用范围

只对 Vue 3 项目中的下列代码生效：`.vue`、`.ts`、`.js`、`.css`、`.less` 和
`.scss`。不适用于 Vue 2、React、Angular、非前端任务，或不在上述范围内的文件。
不要以此 Skill 为由扩大用户任务的技术栈或改动范围。

## 规则读取与应用

1. 在开始改动代码前，读取同目录的 `rules.yaml`。它是唯一机器可读真源；
   `RULES.md` 仅供阅读和评审，不能作为独立规则来源，也不能被手工修改。
2. 只筛选状态为 `ACTIVE` 的规则，并按其 `strength` 执行：
   - `MUST`：本次新增或直接触及的代码必须符合；发现违反时先修正再交付。
   - `GUIDANCE`：优先遵守；项目已有约定或合理例外需要偏离时，说明原因。
   - `VERIFY`：按规则所指的项目既有检查执行，不把它当作代码格式规则。
3. `PENDING` 规则只保留为待确认信息，不擅自执行或提升强度。若任务的实现选择
   必须依赖某条 PENDING 规则，先向用户请求澄清，并说明规则 ID 与未决点；否则在
   交付中列出相关 PENDING 项即可。
4. 规则只约束本次的**触及代码**：新建代码，以及为完成当前任务直接修改的文件和
   区域。不要为统一格式而扩大 diff。
5. 生成或修改模板、渲染函数及交互组件时，逐项执行 `FCS-036` 的可访问名称检查，
   并在交付反馈中记录检查范围、结果及尚未验证的组件或状态。

## 存量代码与冲突边界

- 遇到未触及代码中的存量规范债务，仅报告；不自动重命名、格式化、升级依赖、清理
  插件包，或做跨文件整改。只有用户明确授权规范化迁移时才可处理。
- 如果 `rules.yaml` 与项目的 ESLint、Prettier、Stylelint、TypeScript 或同类自动化
  配置冲突，当前 ACTIVE 规则仅在触及代码中优先。不得因此修改未触及的已有文件。
- 除非用户明确提出“接入规范”或“覆盖工程格式”，不得修改 ESLint、Prettier、
  Stylelint 或同类工程配置。即使有该授权，配置覆盖也仅对触及代码生效；若工具无法
  限定文件范围，或会影响全库检查，先说明影响并等待用户对全库迁移的单独授权。

## 验证与交付

### 识别既有校验

1. 在改动完成后，先读取目标项目的 `package.json`（或项目已有的等效任务清单），
   识别格式化、lint、类型检查和测试脚本；再读取实际存在的相关配置，例如
   ESLint、Prettier、Stylelint、`tsconfig*.json` 和测试工具配置。记录发现的命令
   及其可验证的文件范围。
2. 按本次触及文件和代码性质判断命令是否相关：格式化和 lint 只检查受影响的支持
   文件类型；类型检查只在触及 TypeScript、Vue 类型边界或项目已有命令无法缩小时
   运行；测试只运行覆盖改动行为的既有测试目标。若现有脚本不支持限定范围，不要
   擅自改写脚本或配置来实现限定。
3. 只运行已发现、已安装且与改动相关的既有命令。不临时安装依赖、调用会变更
   文件的自动修复选项，或为验证修改项目配置；第一阶段也不新增自定义规则扫描器。

### 记录校验结论

对每项已发现的相关校验给出一个明确状态：

- **通过**：命令实际运行且退出成功。
- **失败**：命令实际运行但退出失败；记录命令和可审阅的失败摘要。
- **未执行**：命令未运行；记录具体原因，例如与本次改动无关、没有可限定范围的
  安全执行方式、依赖未安装、缺少运行环境，或需要用户额外授权。

失败和未执行都不能写成通过，也不能用“未发现问题”替代实际结果。已发现但与改动
无关的校验同样要以“未执行”记录其不相关原因，避免把它误解为漏检。

### 交付反馈模板

每次实际启用本 Skill，使用下面的统一、可审阅记录交付。保留实际命令、状态和原因，
使多次记录能用于评估试点成熟度与后续规则版本升级；没有内容的栏目填写“无”。
规则版本必须从 `rules.yaml` 的 `version` 字段读取。
交付反馈必须同时列出已运行校验及结果，以及未执行校验及原因。

```text
前端编码规范试点交付反馈
- 规则版本：<rules.yaml 的 version>
- 触发：<显式 | 自动>
- 应用规则：<ACTIVE 的 MUST / GUIDANCE / VERIFY 类别及相关规则 ID>
- 校验结果：
  - <命令或校验名称>：<通过 | 失败 | 未执行> — <范围、摘要或原因>
- 冲突：<项目自动化配置冲突及处理；无则填写“无”>
- 存量规范债务：<仅报告的未触及问题；无则填写“无”>
- PENDING：<相关规则 ID、未决点和是否需要澄清；无则填写“无”>
```

## 试点验收与版本治理

评估试点效果或准备版本升级时，读取 `pilot.yaml` 并逐项执行其中的验收场景；
`PILOT.md` 是由它生成的评审视图，不独立编辑。只有实际执行且留下可复查证据的场景
才能标记为 `PASS`。使用 `scripts/validate_pilot.py` 检查验收覆盖、版本路径、规则阅读
视图一致性和 `overrides.yaml` 边界。

项目级例外以 `overrides.example.yaml` 为结构参考，只能为 ACTIVE 规则新增例外或降级为
`GUIDANCE`，且每项必须记录项目原因与负责人。它不能修改、删除或替换 `rules.yaml`
中的全局规则。试点阶段由本地维护者审批和发布；进入团队插件阶段后，由指定前端
负责人审批规则变更并负责发布。
