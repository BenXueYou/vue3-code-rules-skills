# Vue 3 前端编码规范 Skill（试点）规格

## Problem Statement

团队已有《前端开发编码规范》，其中同时包含 Markdown 文字条款和 PDF 截图示例。当前规范无法被 Codex 稳定、可追溯地应用到代码生成和修改任务：图片中的 good/bad 判断没有结构化表达，规则强度混杂，且缺乏冲突、例外、验证和版本治理机制。

目标是在不改造存量代码的前提下，将该规范转化为可在 Codex 中复用的 Vue 3 Skill。Skill 应在生成或修改代码时约束本次触及代码，提供透明的规则应用与验证反馈，并为后续本机默认规范和团队插件分发建立稳定基础。

## Solution

交付一个版本为 `0.0.1` 的工作区试点 Skill，并以结构化规则清单作为唯一真源。规则清单从原 Markdown 文字条款和 PDF 截图示例共同提炼；Skill 读取该清单，在 Vue 3 代码生成或修改任务中应用 ACTIVE 规则，保留 PENDING 规则供后续澄清。

Skill 显式调用优先，同时允许按任务描述自动触发。它仅修改本次新增或触及的代码，不主动治理存量规范债务。一般情况下不改目标项目的工程配置；只有用户明确要求“接入规范”或“覆盖工程格式”时，才允许调整相应格式与静态检查配置，并仍遵守存量文件不自动迁移的边界。

## User Stories

1. 作为 Vue 3 开发者，我希望显式启用前端编码规范 Skill，以便生成代码时稳定遵守统一规则。
2. 作为 Vue 3 开发者，我希望相关代码任务可自动匹配该 Skill，以便在未显式调用时也获得规范约束。
3. 作为开发者，我希望 Skill 仅调整本次新增或直接修改的代码，以便日常需求不会引发无关的存量格式变更。
4. 作为开发者，我希望未触及的历史违规只被报告而非自动整改，以便控制改动范围和评审风险。
5. 作为开发者，我希望每条规则都有唯一标识、强度、适用范围、判定条件、例外和来源，以便理解和追溯生成约束的依据。
6. 作为规范维护者，我希望 Markdown 条款和 PDF 截图示例被统一沉淀为一个机器可读真源，以便避免多份规范发生漂移。
7. 作为规范维护者，我希望 `MUST`、`VERIFY`、`GUIDANCE` 和 `PENDING` 有清晰的执行语义，以便 Codex 不会将建议或未决规则误作硬性要求。
8. 作为开发者，我希望项目工程格式与 Skill 规则有冲突时，本次触及代码仍遵循当前规则，以便试点能验证规范本身的效果。
9. 作为项目负责人，我希望可以明确授权工程格式覆盖，以便在需要时让项目级 ESLint、Prettier、Stylelint 或同类配置对齐规范。
10. 作为项目负责人，我希望工程格式覆盖不自动格式化存量文件，以便配置接入与全库迁移能分开治理。
11. 作为开发者，我希望 Skill 优先复用项目已有的格式化、lint、类型检查和测试能力，以便不临时引入依赖或篡改项目配置。
12. 作为开发者，我希望在任务交付中看到规则版本、触发方式、验证结果和未决项，以便判断生成结果的规范覆盖度。
13. 作为本地试点维护者，我希望从 `0.0.1` 开始记录规则版本，以便在规则稳定后有序升级到本机默认规范。
14. 作为团队前端负责人，我希望团队插件发布后由受控维护者审批规则变化，以便避免规范真源分叉。
15. 作为项目成员，我希望项目可以声明带负责人和原因的局部例外，以便团队标准能适应真实项目边界而不被直接篡改。

## Implementation Decisions

- 试点仅适用于 Vue 3 项目中的 Vue SFC、TypeScript、JavaScript、CSS、Less 和 SCSS；Vue 2、React、Angular 等框架不在范围内。
- 规则以 `rules.yaml` 作为唯一机器可读真源；由生成工具产出只读的 `RULES.md` 供团队评审，禁止独立编辑阅读视图。
- 每条规则至少包含：唯一 ID、状态（ACTIVE/PENDING）、强度、适用文件或场景、规则内容、判定条件、例外、来源 Markdown 章节和 PDF 页码或截图。
- 原始证据同时由 Markdown 文字条款和 PDF 截图示例构成。真源需记录每条规则的来源，以保留可追溯性。
- 原文中的“必须”“不允许”映射为 `MUST`；“推荐”“统一”“采用”映射为 `GUIDANCE`；项目既有校验命令映射为 `VERIFY`；含义或适用条件不明确的内容记录为 `PENDING`。
- `MUST` 仅约束本次生成或触及的代码。发现未触及的存量规范债务时，默认报告但不自动重命名、格式化、升级依赖或跨文件整改。
- 试点中若当前规则与项目自动化配置冲突，当前规则优先作用于触及代码；不因此改动未触及文件。
- 工程格式覆盖只能由用户明确要求“接入规范”或“覆盖工程格式”触发。若覆盖将造成全库检查影响，或工具不能限定至触及文件，必须先说明影响；全库迁移需要用户单独授权。
- Skill 显式调用优先，同时保留描述驱动的自动触发。每次实际启用后需在交付中声明触发方式。
- 验证时先识别项目已有的格式化、lint、类型检查和测试脚本；仅运行与当前改动相关的既有命令。不为验证临时安装依赖或修改项目配置。无法执行或失败的检查必须报告。
- 第一阶段不开发自定义规则扫描器。高频且稳定的违规规则将在试点后再评估自动化实现。
- 团队阶段允许项目提供独立的 `overrides.yaml`：它只能新增例外或将规则降级为 `GUIDANCE`，且必须包含项目原因与负责人；不得改写全局规则真源。
- 版本从 `0.0.1` 起步；完成首轮规则清单、Skill 和真实项目验证后升级至 `0.1.0`；团队插件正式发布并承诺兼容性后升级至 `1.0.0`。
- 第一阶段由本地维护者维护规则真源；团队阶段由指定前端负责人审批规则变更并负责发布。

## Testing Decisions

- 最高层验证切面是一次真实 Vue 3 代码生成或修改任务的可观察交付行为：Skill 是否启用、是否只修改触及代码、是否应用 ACTIVE 规则、是否报告验证与未决项。该切面优先于为每条规则新建内部实现测试。
- 规则真源的结构验证应检查版本、规则 ID 唯一性、必填字段、状态和强度枚举、来源信息，以及项目级覆盖文件的允许操作范围。
- 阅读视图生成验证应确保其内容来自同一真源，并标示规则版本和状态；不对手工修改的阅读视图提供支持。
- Skill 行为验证应覆盖显式触发、自动触发、未触及存量文件保护、PENDING 规则不执行、MUST/GUIDANCE 区别、项目格式覆盖授权和全库迁移需额外授权等外部行为。
- 项目验证应优先执行项目既有的格式化、lint、类型检查和测试命令。测试结论必须区分：通过、失败与未执行，并记录原因。
- 当前工作区没有可复用的测试基础设施或同类 Skill 测试先例；实现时应避免为试点引入额外测试框架。

## Out of Scope

- 对未触及存量文件进行自动格式化、重命名、依赖清理或跨文件规范化迁移。
- Vue 2、React、Angular 或其他非 Vue 3 技术栈的规则支持。
- 第一阶段编写自定义静态扫描器、全局 CI 门禁或自动修复器。
- 未经明确授权修改目标项目工程格式配置。
- 团队插件的实际发布、市场分发和安装流程；它们属于试点稳定后的后续阶段。
- 让项目级覆盖文件改写或删除团队全局规则。

## Further Notes

- 试点交付反馈至少包含：规则版本、显式或自动触发状态、应用的规则类别、已运行校验及结果、未执行校验、冲突和 PENDING 项。
- 试点到本机默认规范的推进依据是规则与例外在真实任务中趋于稳定，而不是只凭版本号升级。
- 当前工作区未发现 Git 仓库或已配置的 issue tracker，因此本规格未发布到外部 issue tracker，也无法应用 `ready-for-agent` 标签。
